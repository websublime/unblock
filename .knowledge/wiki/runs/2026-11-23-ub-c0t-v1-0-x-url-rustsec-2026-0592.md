## What & why

The advisory: in url 2.5.8 and earlier, `Url::origin` handles a `blob:` URL by parsing its path as
another URL and calling itself on the result, whatever the inner scheme, so each nested `blob:`
prefix costs one stack frame with no depth limit, and a long enough chain overflows the stack and
aborts the process. `url::quirks::origin` goes through the same function. url 2.5.9 is the patched
floor (`patched = [">= 2.5.9"]`): its `origin.rs` follows the inner URL of a `blob:` path only when
the inner scheme is `http`, `https` or `file`, so recursion stops after one level. The advisory is
dated 2026-11-20 and reached advisory-db at commit `248aea09` on
2026-11-22. It first showed up red on #483 and #484 (ub-b9z), whose own diffs touch no lock; on the
1.0 side, run 45147224804 of #484 failed `deny` and `audit` on this id alone.

Why now: the v1.0.4 cut. 1.0 `RELEASING.md:229-230` asks that "the push CI run on the branch head is
green", and a single red job makes the run's conclusion `failure`. The last 1.0 push run (44535938720
on `b21c73bd`) is green only because it predates the advisory; any new head on the release line,
#484's merge included, gets a fresh run that is green only once url is bumped.

The exposure is nil on this line. url has five dependents in the lock — axoasset 2.0.1, axoupdater
0.10.0, reqwest 0.13.4, tower-http 0.6.11, and wiremock 0.6.5 as a dev-dependency of
`unblock-cli` — and no unblock crate depends on it directly. It reaches the shipped binary only
through the default `self-update` feature (`self-update = ["dep:axoupdater"]`); with
`--no-default-features` the inverse tree prints nothing. Nothing calls the vulnerable functions:
`crates/` and `xtask/` have zero callers, and so have the registry sources of all five dependents.
reqwest decides whether a cross-host redirect keeps its headers by comparing `host_str()` and
`port_or_known_default()`, not `origin()` (`reqwest-0.13.4/src/redirect.rs:239-242`). cargo-audit
and cargo-deny match on the lockfile version, not on the call graph, so both jobs were red anyway.

url 2.5.9 also changes other behaviour: the path percent-encode set gains `^`, a `file:` URL with a
host and a drive-letter path keeps its host, a backslash ends a port only for special schemes, the
quadratic `..` parsing is fixed, and form_urlencoded 1.2.3's `Serializer::for_suffix` clamps
instead of panicking. [INFERENCE] None of these touches a GitHub API or release-asset URL that
`unblock update` builds or follows; the wiremock cells in `crates/unblock-cli/tests/update_verify.rs`
drive that path, and they pass.

The command, run on this line's own base rather than cherry-picked from `main` (the offsets, the
package count and the edge count differ), is `cargo update -p url --precise 2.5.9` (ruling 513 item
1). form_urlencoded 1.2.2 to 1.2.3 is forced, because url 2.5.9's manifest requires
`form_urlencoded = "1.2.3"`. The reproducibility witness is a plain `cargo update -p url` in a fresh
`git archive b21c73bd` tree, whose lock is byte-identical to the committed one (`cmp` exit 0). The
post-lock sha256 is `c8e8ca92d2eff8894e6b3805667fb0d86ad62cc66b881506aa41939abd4b0781`.

## Gotchas

- `bench-gate` failed attempt 1 on runner noise, not on this change. The whole runner was slow:
  unrelated benchmarks ran 1.5 to 3.3 times slower on attempt 1 than on attempt 2, with the same
  code. url and form_urlencoded are not in `unblock-policy`'s dependency graph, where
  `cmp_ready_sort` lives (`cargo tree -p unblock-policy -i url` exits 101, no match). In 15 earlier
  green runs the mean ranged from 218.9 ms to 485.7 ms, two of them 14.3 ms and 18.9 ms below the
  ceiling. Finding ub-8f4 tracks the noise and the ceiling. Until it lands, Miguel's interim
  practice (comment 521) is: re-run once, only when `bench-gate` is the only red job and the noise
  evidence looks like this attempt-1 case, record both attempts, and a green re-run counts as a
  green push run for the v1.0.4 cut.
- In the agents' tool shell the in-process `grep` builtin rejects a POSIX bracket expression that
  the system grep accepts, and the d59 claims script (on `main`) treats that error as "no match", so
  its forbidden-line rows pass vacuously with exit 0 (finding ub-1k3). This line has no d59 script,
  but the same rule applies to every local claims-script run: `env -i PATH=/usr/bin:/bin /bin/sh
  scripts/checks/<script>.sh`, and any `regex parse error` line voids the run.
- On `main`, the pull-request `audit` is green only through rustsec/audit-check's fallback path,
  and the push `audit` stays red after the merge for a reason unrelated to url (finding ub-c77). On
  this line the ignores leave 0 warnings, so both runs take the early return and both are expected
  green.
- [INFERENCE] The 1.0 push run is the fragile one: a new unmaintained, unsound or yanked warning in
  the advisory DB would turn only the push `audit` red, because a pull-request run takes the
  fallback and passes. That is why the v1.0.4 cut reads the push run.
- `deny` and `audit` are required checks on neither line, so a red advisory gate does not block a
  merge by itself; Miguel does not merge red pull requests (ruling 513 item 3).
- The full local Windows cross-check of `unblock-cli` exits 101 on macOS for environmental reasons
  (the aws-lc-sys and libsql-ffi C builds lack `windows.h`). CI `windows-check` is the authority; the
  Windows-target check of the two changed crates passes locally.
- 1.0 only: a fresh whole-tracker export on top of an older report that lists ub-c15 is a k6 trap —
  ub-c15's later comments fall under that report's glossary scan, so the export, the run-report and
  the 44 rows have to land in one commit.
- Tracker comments on `ub-c0t` stay free of session-local ids, code spans included: k6 scans them
  for every report of an equal or later date, and gate rule 1a scans the raw export line.
- The tool shell rewrote `git worktree add` into a copy-on-write clone of the main checkout, which
  copied its ignored files (`target/` and the live tracker database among them). Implement deleted
  the copied database files inside the worktree only and set the upstream by hand.
