## What & why

RUSTSEC-2026-0592 (GHSA-hrj5-67jp-wqp9): in url 2.5.8 and earlier, `url::Url::origin` and
`url::quirks::origin` recurse without limit on nested `blob:` URLs, so a crafted URL exhausts the
stack. The patched floor is 2.5.9, the first and newest patched release; its `origin.rs` recurses
into a `blob:` path only when the inner scheme is `http`, `https` or `file`, so recursion stops after
one level. The advisory entered advisory-db at `248aea09` (2026-11-22 09:48Z). It first showed up red
on the ub-b9z pull requests: #483 (run 45147213629) and #484 (run 45147224804) failed `deny` and
`audit` on it without touching a lock.

Why now: Miguel does not merge red pull requests, and the v1.0.4 cut needs a green release-line push
run (1.0 `RELEASING.md:229-230`), whose `audit` job fails on this advisory. ub-b9z's #483 and #484
therefore wait for both url pull requests (ruling 513 item 3).

Exposure verdict: none for users; the impact is on CI and on the cut precondition, the same shape as
`ub-5xl`.
- Five lock entries depend on url: axoasset 2.0.1, axoupdater 0.10.0, reqwest 0.13.4, tower-http
  0.6.11, and wiremock 0.6.5 as a dev-dependency of unblock-cli. No unblock crate depends on url
  directly.
- url reaches the shipped binary only through the default `self-update` feature
  (`self-update = ["dep:axoupdater"]`); without default features unblock-cli has no normal path to
  url.
- Nothing calls the vulnerable functions: zero callers in `crates/` and `xtask/`, and zero in the
  five dependents' registry sources at their locked versions. reqwest decides whether to strip
  headers on a cross-host redirect by comparing `host_str()` and `port_or_known_default()`
  (`reqwest-0.13.4/src/redirect.rs:239-242`), not `origin()`.
- cargo-audit and cargo-deny match on lockfile versions, not on the call graph, so both gates were
  red anyway.

The other behaviour changes in url 2.5.9: the path percent-encode set gains `^`; a `file:` URL with
a host and a drive-letter path keeps its host; a backslash ends a port only for special schemes; the
quadratic `..` parsing is fixed; form_urlencoded's `Serializer::for_suffix` now clamps instead of
panicking. [INFERENCE] None of these changes a GitHub API or release-asset URL that `unblock update`
builds or follows; the wiremock cells in `crates/unblock-cli/tests/update_verify.rs` exercise that
path and pass (16 passed, Verify supply lens).

The command, on `b3f63b95` (ruling 513 item 1):

```sh
cargo update -p url --precise 2.5.9
```

The witness: a plain `cargo update -p url` on a fresh archive of `b3f63b95` produces a
byte-identical lock (`cmp` exit 0), and so does the `--precise` command; Verify re-ran both. Lock
sha256 before `431a8802095103f5f614831c3c65c8d129c8f78af78c9680e36067e8c6e2d7cd`, after
`f0fb5035befa5710fac9219ff4c7d604c5babb6f121738b16ec36959e8712160`.

## Gotchas

- Main's `audit` is green on a pull request only through the action's fallback: with a warning
  present it calls the Checks API, gets a 403, and on a pull request falls back without failing. On
  the push run after merge the 403 is rethrown, so main's push `audit` stays red, as it has been on
  every main push since 2026-11-17. That is `ub-c77` (ruling 513 item 4), unrelated to url; the push
  run is judged by its log (0 vulnerabilities, the chrono warning, and `Resource not accessible by
  integration` as the only error).
- [INFERENCE] The 1.0 line's `audit` has the opposite fragility: its two dated ignores leave no
  warning, so the action returns early, and any new unmaintained, unsound or yanked warning turns
  only the push run red while pull-request runs stay green.
- `deny` and `audit` are not required checks on either line; a pull request with both red still
  shows `mergeStateStatus` UNSTABLE and is mergeable. Never call them required.
- The local Windows cross-check of the whole package (`cargo check -p unblock-cli --locked --target
  x86_64-pc-windows-msvc`) exits 101 on both the base and the bumped lock, because the aws-lc-sys and
  libsql-ffi C builds find no `windows.h` on macOS. The failure is environmental; CI `windows-check`
  is the authority.
- In the agents' tool shell the in-process `grep` rejects the POSIX bracket expression of
  `d59-rmcp3-claims.sh:87`, and the script still prints its OK line with exit 0, so its forbidden-line
  rows pass vacuously. Run claims scripts as `env -i PATH=/usr/bin:/bin /bin/sh
  scripts/checks/<script>.sh`, and treat any `regex parse error` line as a void run; the fix is
  `ub-1k3`.
- The tool shell turned `git worktree add` into a copy-on-write clone of the main checkout, ignored
  files included; the implementer removed the copies inside its own worktree (`git clean -fdX`)
  without touching the main checkout or the live tracker database.
- GitHub's "Rebase and merge" rewrites every SHA on landing, even for an up-to-date pull request,
  so the SHAs above are the PR-branch ones; the tracker comments name the landed tips.
- Every `ub-c0t` tracker comment stays free of session-local ids, code spans included: knowledge-lint
  k6 scans the comments dated on or before each `ub-c0t` report, and rule 1a of the run-report gate
  scans the raw exported line.
