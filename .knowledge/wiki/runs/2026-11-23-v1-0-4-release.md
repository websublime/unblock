# Run — the v1.0.4 release and the v1.0.3 → v1.0.4 live update smoke

## Context

This records the v1.0.4 cut and its record on `main`: step 6 of section 5.4 of the `ub-b9z` plan (v2.1), as
amended by section 8.2 of the `ub-c0t` plan (v1), under `docs/PROCESS.md` §6 and §8. The fix landed on
`release/v1.0.x` as PR #484 (merged 2026-11-23T13:59:04Z, tip `8f97a9bd`), after its `main` sibling PR #483
(13:52:37Z, tip `23db3833`). Both merged after the `ub-c0t` url lock bumps, PR #485 on `main` (12:53:54Z) and
PR #486 on `release/v1.0.x` (12:54:07Z), by Miguel's merge order (tracker comments 513 and 514). The release
commit is `430752ce` ("release: v1.0.4") on `release/v1.0.x`. This record is on the branch
`ub-b9z-v1-0-4-record` off `main` `23db3833`.

## What & why

These were read rather than restated here: the 1.0 line's `RELEASING.md` §5 and §6, ci-cd §3.3 and §4, and
the `v1.0.4` subsection of roadmap §1. After the cut the roadmap, `CLAUDE.md`, T3.19 of the implementation
plan, ci-cd §4 and the published `docs/roadmap.html` still described v1.0.4 as planned and the
`v1.0.3 → v1.0.4` smoke as future, and PRD NFR-7 on `main` did not say that the 1.0 line carries the same
rule. Recording both closes that drift, as the v1.0.3 record did, and closes `ub-b9z`.

The 1.0 line's `RELEASING.md` §6 step 1 has a 1.0.x run-report land in its own pull request "and again in
the record pull request on `main`", so the `ub-b9z` and `ub-c0t` 1.0-line reports land here as main copies.
The run-reports keep their pull-request branch SHAs; Miguel ruled that this record lists the landed ones
(tracker comment 518, item 4), which the section "Landed commits" below does. Miguel also ruled that the
v1.0.4 slot gains a known-advisories bullet for the url bump (tracker comments 513 and 514).

### Known advisories

- url 2.5.8 → 2.5.9 (RUSTSEC-2026-0592, a stack overflow in `Url::origin` on nested `blob:` URLs), which
  forces form_urlencoded 1.2.2 → 1.2.3, by a semver-compatible `Cargo.lock`-only bump on both lines
  (`ub-c0t`, PRs #485 and #486). Nothing in unblock or in its url dependents calls `Url::origin`, so the
  shipped binary never reached the vulnerable code; the cost fell on the red `deny` and `audit` jobs and on
  the cut precondition.
- RUSTSEC-2026-0462 (rmcp 1.7's streamable-HTTP client, not compiled) and RUSTSEC-2026-0543 (chrono,
  unmaintained) keep their dated ignores on the 1.0 line (`ub-kpe`, tracker comment 446); neither url pull
  request changed an ignore, and the release-line `audit` logged no vulnerability and no warning.
- `main`'s push `audit` stays red on the chrono warning followed by a `403` on the action's check-run call
  (`ub-c77`). Main push run 45188279526 on `23db3833` was green on every other job, `deny` included. This
  does not touch v1.0.4; it blocks `main`'s green-push precondition for v1.1.0.

## Gotchas

- GitHub's `macos-15` runner capacity: the required macOS exclusivity job got no runner twice the same day,
  on PR #484 (tracker comment 527) and on the release-line push run. Each time a re-run of that job alone
  went green. A green re-run as cut evidence needed Miguel's ruling, since the recorded re-run practice
  covers only `bench-gate` (`ub-8f4`).
- Rebase merging gives every landed commit a new SHA, so the run-reports' commit lists name pull-request
  branch commits that are not on either line; the landed list above is the map.
- The `pr:` field of this report and of the two copies stays `pending` until this pull request has a
  number: the pr-create hook refuses `gh pr create` until a run-report is in the branch diff.
- `ub-y72` (the intermittent `content_hash` fuzz failure) did not recur and stays open.
