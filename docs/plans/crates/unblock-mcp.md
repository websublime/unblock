## Pinned rmcp 1.7 API contract (the build-against surface — RK-2; resolves OQ-1/OQ-2)

All facts below are **READ FROM VENDORED SOURCE** (`rmcp-1.7.0` / `rmcp-macros-1.7.0`), not memory — they replace the OQ-1/OQ-2 uncertainty with the confirmed contract. They are the normative shape this crate builds against; the `#![forbid(unsafe_code)]` invariant holds (nothing in the rmcp surface we touch needs unsafe).

- **Tool/prompt macros.** `#[tool]` / `#[tool_router]` / `#[tool_handler]` (and `#[prompt]` / `#[prompt_router]` / `#[prompt_handler]`) — methods on `&self`. `#[tool_router]` generates `Self::tool_router() -> ToolRouter<Self>`; `#[tool_handler]` wires `call_tool`/`list_tools` + a `get_info().enable_tools()`. Routers compose via `Add`/`merge`; rebuild-per-call is fine (schemas are cached per `TypeId`), so storing the router in a field is optional.
- **Typed args via the `Parameters<T>` extractor.** A tool/prompt fn takes `Parameters(args): Parameters<T>` where `T: rmcp::schemars::JsonSchema + serde::Deserialize`. The per-tool input schema is the draft-2020-12 `JsonSchema` of `T`. **D42: we do NOT use rmcp's `Parameters` — we shadow it.** rmcp's extractor deserializes `T` inside itself and maps any failure to `ErrorData::invalid_params`, an OUT-OF-BAND `-32602` that escapes the FR-11 in-band channel. A crate-local `Parameters<T>` (`src/tools/args.rs`) stores the raw `JsonObject` instead, so its `FromContextPart` impl is infallible and that arm is UNREACHABLE for our 8 tools; the typed parse moves into the tool body, where a failure becomes an in-band `StructuredError`. **The name `Parameters` is LOAD-BEARING** — rmcp-macros picks the published `inputSchema` by matching the last path-segment ident, so any other name silently collapses all 8 schemas to `schema_for_empty_input()`. `ErrorData` stays reserved for TRUE protocol faults: an unknown tool name, a non-object `arguments`, a present `params.task`, and resource paths. **D43 — WHAT THIS SEAM STRUCTURALLY CANNOT SEE.** `from_context_part` takes `context.arguments`, a `serde_json::Map` rmcp ALREADY BUILT while decoding the frame. A duplicated JSON key was collapsed last-wins at that build, so the shadowed member is gone before this type exists — neither the extractor, nor `parse_args`, nor `deny_unknown_fields` can EVER observe it. **No fix can live here**; detection has to own the read framing (`src/wire.rs`) and arrives as a verdict on `RequestContext.extensions`, where **absent ⇒ REJECT**. Read that typemap DIRECTLY — rmcp's `Extension<T>` extractor must NOT be used: its absent arm is `ErrorData::invalid_params` ⇒ `-32602`, exactly the out-of-band arm this seam exists to keep shut. **`schemars` is pinned via the `rmcp::schemars` re-export** so the derive macro and rmcp see the identical schemars version (workspace `schemars = "1"` matches rmcp 1.7).
- **`ServerHandler`.** `trait ServerHandler: Sized + Send + Sync + 'static` — **all 26 methods are provided, ZERO are required**, and `impl ServerHandler for Arc<T>` exists. So the handler holds `Arc<Session>` and is itself Send+Sync. Capabilities are advertised by overriding `get_info()` → `ServerCapabilities::builder().enable_tools().enable_prompts().enable_resources()`.
- **Resources — NO macro, NO router, NO URI-template matcher.** rmcp's `resource.rs` is EMPTY. `ResourceTemplate`/`RawResourceTemplate::new(uri_template, name)` exist to *advertise* the `unblock://issues/{id}` string, but rmcp routes `read_resource` by the raw `params.uri: String` only — there is no built-in `{id}` extractor. Therefore we **HAND-WRITE `get_info()`** (to add `.enable_resources()`) plus `list_resource_templates`/`read_resource`, and **HAND-PARSE `{id}` from `params.uri`** (strip the `unblock://issues/` prefix); an unmatched/unknown uri → `ErrorData::resource_not_found` (`-32002`). (Because resources have no handler macro, `get_info` cannot be macro-generated alongside tools+prompts: stack `#[tool_handler]` + `#[prompt_handler]` + the hand-written resource methods on ONE `impl ServerHandler`, do NOT use `#[tool_router(server_handler)]`, and do NOT let two macros both emit `get_info` — write it once by hand.)
- **In-band domain-error channel (resolves OQ-2).** `CallToolResult::structured_error(json)` carries `content` (a text mirror) + structured `data` + `is_error = Some(true)` in ONE result — i.e. a single call can return valid-JSON content AND `isError=true` AND structured `data`. **Domain errors → in-band `structured_error`** (FR-11, always-valid-JSON). **D42 EXTENDS this: argument-deserialization failures (unknown/missing/mistyped fields, over-quota requests) now route in-band too**, scoped as above. `Err(ErrorData{code,message,data})` is reserved for **true protocol faults** (transport/serialization/auth-level) only.
- **stdio + cooperative shutdown (FR-17, resolves OQ-1 transport).** `handler.serve_with_ct(rmcp::transport::stdio(), ct).await?.waiting().await?`, where `ct` is rmcp's plumbed-through `tokio_util::sync::CancellationToken`; a SIGINT/SIGTERM handler calls `ct.cancel()`. **Cancel is two-outcome (D38 — spine `01-design-spine.md` §0.1 corrects the earlier unconditional "drains in-flight and returns cleanly" claim):** it drains in-flight work and returns `Ok(())` **only if the rmcp `initialize` handshake already completed**; rmcp's `serve_server_with_ct` wraps the WHOLE handshake in a `select!` against `ct.cancelled()`, so a cancel landing **during** the handshake returns `Err(ServerInitializeError::Cancelled)` → `McpServerError::Transport`. **Both** are normal cooperative-shutdown outcomes; the caller MUST NOT treat the `Err` as an independent fault (spine §5b). (`transport::stdio()` needs the `transport-io` feature ✅. **Add `tokio-util = "0.7"` to the crate deps** for the token.)
- **Quotas have NO rmcp hook (NFR-18).** rmcp provides NO built-in request-size / array-length / string-length / per-tool-concurrency / batch cap on the stdio path, and there is no middleware layer for stdio (the `tower` layer is streamable-HTTP only). Therefore the `Quotas` limits MUST be enforced by a shared `enforce_quota` call **ONCE in `call_tool`, over the whole `CallToolRequestParams` (plus `RequestContext.meta`, where rmcp has moved `_meta` by then), inside the rate-limit permit and BEFORE dispatch** (D42) — returning an in-band error on breach. **The pre-D42 prescription — per tool body, AFTER `Parameters<T>` deserialization — is what CAUSED the bypass:** it measured a re-serialized TYPED value, in which anything the client parked under an unknown key simply did not appear. **D43 — rmcp has no DUPLICATE-KEY hook either, and a `Transport` DECORATOR cannot substitute for one.** `VersionClampingTransport::receive` (`src/server.rs`) receives an ALREADY-PARSED `RxJsonRpcMessage`, one layer too late — same impossibility as the argument seam, one level up. So the scan must **OWN the byte framing**: `src/wire.rs` is a hand-written `Transport<RoleServer>` that reproduces ALL of `AsyncRwTransport::receive` (the `read_until` line read with no length bound, EOF, the single `\n` then single `\r` strip, the blank-line skip, the one-shot prefix BOM strip, the compatibility filter that silently ignores unknown client notifications, and the `-32700` parse-error reply with the id OMITTED followed by RECOVERY on the next line) and inserts the scan between the read and the parse. Those helpers are PRIVATE to rmcp, so this is a FORK of an undocumented internal, pinned as **CD-7** by a differential harness that feeds one byte corpus to both transports and asserts identical `receive()` sequences and identical bytes written. Dropping the compatibility filter would make us answer `-32700` to an unknown client NOTIFICATION — a JSON-RPC violation. (Per-workspace write serialization stays the `unblock-engine` tokio `Semaphore` (in-process, D14), which now composes ABOVE the storage cross-process `.unblock/.write.lock` (D31, an L2 primitive) — rmcp gives no write lock, and MCP does not duplicate either.)

## Open questions (specific to this crate)

- **OQ-1 (rmcp 1.7 API surface, RK-2) — RESOLVED (T2.2).** The rmcp 1.7 API is PINNED from vendored source in the "Pinned rmcp 1.7 API contract" section above: `#[tool]`/`#[tool_router]`/`#[tool_handler]` (+ `#[prompt*]`) macros; typed args via `Parameters<T>`; `ServerHandler` all-26-methods-provided with `impl ServerHandler for Arc<T>`; resources have NO macro/router/URI-template matcher (we hand-write `get_info`/`list_resource_templates`/`read_resource` and hand-parse `{id}` from `params.uri`); rmcp gives NO built-in request-size/quota cap on stdio, so `Quotas` is enforced by `enforce_quota(&args)` inside each tool body.
