- **Status:** DRAFT — for review. Conforms to `docs/plans/01-design-spine.md` §3 (AUTHORITATIVE interface contract) and `docs/plans/00-roadmap.md`. APIs here MUST NOT drift from the spine without amending it first.

## 1. Purpose / Layer / Depends-on

- **One-line purpose:** Define the backend-agnostic async `Storage` trait and provide the **only** backend-aware implementation (libsql), owning schema, migrations, prepared queries, transactional mutate (rows + audit events together), WAL + native `busy_timeout` non-spin discipline (NFR-3), and the remote/replica path behind a non-default feature (D15).
- **Layer:** L2.
- **Depends on (acyclic, NFR-15 / spine §0):** `unblock-model` (L0) + `unblock-error` (L0) **only**. NOT `unblock-policy` (CF-11 fix — the engine at L5 composes storage + policy; any contract type both need lives in `unblock-model`, e.g. `CacheKey`). NOT `tracing` for domain logic beyond the `unblock.reliability` target seam. Backend crate (`libsql`) is a **private** dependency: no libsql type may appear in any public signature (spine §6 rule 2; libsql errors absorbed into `StorageError::Backend { source: BackendOpaque }`).
- **Invariant gates this crate owns:** RK-1 / NFR-3 contention lab (M0 exit gate, before any crate depends on storage); NFR-16 backend-independent `Storage` contract suite; RK-4 (remote feature keeps TLS/HTTP off the default build — verified by `cargo-deny` on the default feature set).

## 2. Public API summary (what other crates import)

### v1 (LOCKED)
> **v1 matrix note (G-24d):** the remote/replica path is **off by default in v1** — `feature = "remote"` is non-default and the v1 default build ships local-libsql only (D15). The remote constructors/types below are fenced to v1.2.

Re-exported from `lib.rs`:
- **Trait:** `Storage` (async, `Send + Sync`) — spine §3.2 (full method set).
- **Query/result contract types (defined in `unblock-model` §1.10, RE-EXPORTED here — CF-A/CF-C):** `ListFilters`, `CountGroupBy`, `CountBucket`, `GraphEdge`, `DepTree` via `pub use unblock_model::{...}`. unblock-storage does **not** define these (unblock-policy needs `ListFilters` for its filter-fingerprint but cannot depend on storage; unblock-render formats `CountBucket`/`DepTree` with model+error only).
- **Storage-owned types (defined here):** `DeletePlan`, `DeleteMode`, `IssuePatch` — spine §3.1.
- **Backend constructor:** `LibsqlStorage` (the concrete impl) + `LibsqlStorage::open_local(path: &Path) -> Result<Self, StorageError>` and `open_in_memory()` (tests). No libsql types exposed.
- **Error:** `StorageError` (snafu, spine §2.1) + `impl StorageError { fn code(&self) -> unblock_error::ErrorCode }`, plus `hint()`/`retryable()` views. `BackendOpaque` is **public-but-opaque** (Debug/Display only; no inner libsql type reachable).
- **Test support (behind `pub` in a `testkit` module, gated `#[cfg(any(test, feature = "testkit"))]`):** the contract-suite entry `run_storage_contract_suite<S: Storage>(factory)` so a future backend reuses it (roadmap v2+ pluggable-backends seam).

### v1.1 (LOCKED — additive only, no topology change)
- Trait grows (additive): label rename/list-all, comment add/list, epic rollup queries, saved-query CRUD, DB config-table accessors. New supporting types: `LabelRename`, `SavedQuery`, `ConfigKv`. `EpicStatus` (already in model) returned from `epic_status(id)`.
- **Reserved v1.1-additive seams pinned now (CF-E, spine §3.2):** `read_config(&self) -> Result<Vec<(String, String)>, StorageError>` (persisted key/value config rows — backs the config db-layer), and full-taxonomy `diagnostic_probe(&self, kind: DiagnosticKind) -> Result<DiagnosticReport, StorageError>` + `diagnostic_probes(&self) -> Result<Vec<DiagnosticReport>, StorageError>` (back health full-taxonomy). Signatures are pinned in v1 so dependents compile; v1 impls may return empty / `NothingToDo`. `DiagnosticKind`/`DiagnosticReport`/`DiagnosticFinding` are defined in `unblock-model` §1.10 (CF-B) and **re-exported here** (`DiagnosticFinding` travels inside `DiagnosticReport`, so storage re-exports it for CF-E seam consumers — G-10).

### v1.2 (PROPOSED — the heart of this release)
- `LibsqlStorage::open_remote(...)` / `open_replica(...)` **behind `feature = "remote"`** (off by default, D15). New: `SyncState`, `SyncReport`, `ReplicaLag`. Credentials never accepted as struct fields sourced from `config.toml` — only via caller-passed token resolved upstream from `UNBLOCK_*`/keychain (NFR-18).

### v1.3 (PROPOSED)
- Archival/compaction methods (`compact`, `restore_snapshot`), batch/streaming read variants, perf-tuned indexes. Additive; `contract_version` bump handled at L7.

> Stability rule: every change v1.1→v1.3 is **additive** to the trait (default-method or new method) so engine/MCP `contract_version` bumps stay non-breaking (spine §6 rule 6).

## 4. Crate-level test & bench plan

- **Contract suite (NFR-16):** every `Storage` method has ≥1 contract case in `testkit.rs`, run against libsql (local file + in-memory) in `tests/contract.rs`. This is the reusable proof for the v2+ pluggable-backend seam.
- **Contention lab (NFR-3 / RK-1):** `tests/contention_lab.rs` is the **M0 hard exit gate** — must pass before any L3+ crate depends on storage. Asserts atomic-claim correctness (FR-2 AC) and no CPU hot-spin (defect-243 cannot recur by construction: WAL + native busy_timeout + serialized writer).
- **proptest:** content_hash recompute-on-load stability; `IssuePatch` apply order-independence; row↔domain round-trip (`mappers.rs`); id uniqueness; cycle-detector termination.
- **insta snapshots:** `PRAGMA table_info(issues)` column order; index list; `StorageError → ErrorCode` map (mirrors `unblock-error` golden).
- **criterion:** NFR-1 budgets (`benches/storage.rs`), 10% regression gate; v1.3 adds 1M-issue NFR-2 CI gate.
- **cargo-deny / cargo-tree:** default feature set has **zero** TLS/HTTP/network crates (RK-4 / NFR-10); retry crate is maintained (`backon`/`tokio-retry`, not `backoff 0.4`); no git crate / `Command::new("git")` (NFR-6).
- **wiremock (v1.2, `remote` only):** remote contract suite + bounded-retry/circuit-breaker behaviour.

## 5. Open questions specific to this crate

- **OQ-1 (search backend):** Original uses **LIKE** (no FTS5 virtual table). v1 reproduces LIKE for behaviour fidelity + zero extra surface. Should v1.3 introduce an FTS5 contentless index for the 1M-issue search budget, or keep LIKE + the `idx_issues_*` indexes? (Decision deferred to v1.3 perf work; FTS5 availability in bundled libsql must be confirmed.) **Do not simplify away** — flag for Miguel if LIKE misses NFR-1 search budget.
- **OQ-2 (busy_timeout value):** What concrete `busy_timeout` ms balances non-spin vs latency under the contention lab? Tune empirically in T0.8; record the chosen value as a schema/pragma constant.
- **OQ-3 (ready ordering ownership):** Spine says hybrid sort is applied by the **engine via policy** (L5), but storage must return a deterministic candidate ordering for stable snapshots (NFR-14) and for the `idx_issues_ready` perf path. Confirm: storage returns the unblocked+undeferred set ordered by the index (priority, created_at) and the engine re-ranks; storage never imports policy (CF-11). Verify this split doesn't force a second full sort at scale.
- **OQ-7 (contract-type ownership) — RESOLVED (CF-A/CF-B/CF-C, spine §1.10):** `ListFilters`, `CountGroupBy`, `CountBucket`, `GraphEdge`, `DepTree` are now defined normatively in `unblock-model` §1.10 and **re-exported** from this crate; storage defines only `DeletePlan`/`DeleteMode`/`IssuePatch`. Rationale: unblock-policy needs `ListFilters` for its filter-fingerprint but must not depend on storage, and unblock-render (model+error only) must format `CountBucket`/`DepTree`. Layering unchanged — types moved *down* to L0 model; storage still depends on model+error only. `DiagnosticKind`/`DiagnosticReport` likewise live in model §1.10 (CF-B) and back the CF-E diagnostic-probe seams.
- **OQ-4 (blocked/ready cache):** Original persisted `blocked_issues_cache`; this plan drops it and computes live via SQL/petgraph. Confirm live computation meets the ready 10k <50ms budget (NFR-1) at 250k (NFR-2); if not, reintroduce a projection table in v1.3 (additive) rather than v1.
- **OQ-5 (pool vs single connection under D14):** With one serve process + in-process write Semaphore (engine), does storage hold a single libsql `Connection` for writes + a read pool, or one shared handle? Affects WAL reader concurrency (FR-10). Decide in T0.6; must not change the public API.
- **OQ-6 (multi-writer reconciliation, v1.2):** last-write-wins on `content_hash` vs operation log for remote sync (roadmap §3 risk) — a v1.2 design decision that lands in `remote.rs`; do not pre-bake into v1 schema beyond reserving room.
