# unblock-policy — File-level Plan

- **Status:** DRAFT — per-crate plan, conforms to `docs/plans/01-design-spine.md` (AUTHORITATIVE) + `docs/plans/00-roadmap.md` + `docs/PRD.md` (PRD APPROVED v1.1).
- **Date:** 2026-06-19
- **One-line purpose:** Pure, side-effect-free, **versioned decision contracts** — ready/scheduler ranking, swarm-coordination diagnosis, gates/close-policy evaluation, context inheritance selection, and cache policy kernels — consumed by `unblock-engine` (L5) and exposed (read-only) through `unblock-mcp` (L7).
- **Layer:** **L1** (spine: `L0 model | error → L1 policy → L2 storage → …`). A pure leaf above model/error.
- **Depends on:** `unblock-model`, `unblock-error` **only** (PRD §8.1 / spine §0 / NFR-15). **No** `storage`, `sync`, `config`, `tokio`, I/O, `petgraph`, or any backend. All inputs are caller-supplied plain data; all outputs are plain data. `#![forbid(unsafe_code)]`, `#![warn(missing_docs)]`, clippy pedantic.
  - **Acyclic invariant:** policy must never reach upward. The engine composes `storage + policy` (CF-11 fix); the cache-key *contract type* `CacheKey` lives in `unblock-model` (spine §1.9) precisely so both policy and storage can name it without a policy↔storage edge. unblock-policy may *consume* `unblock_model::CacheKey` but does not define it. The query/filter contract types `ListFilters` and `CountGroupBy` likewise live in `unblock-model` (spine §1.10, CF-C) — relocated there so policy can fingerprint over `ListFilters` without a policy→storage edge; storage re-exports them. Policy consumes `unblock_model::{ListFilters, CountGroupBy}` and never defines them. **Derive note (G-1/G-15):** the spine §1.10 derive-policy paragraph now applies the full set (`Debug, Clone, Serialize, Deserialize, JsonSchema` + `PartialEq, Eq`) to **every** §1.10 type incl. `ListFilters` and `CountGroupBy`, so any policy type that embeds them (`SchedulerInput`, `NormalizedFilters`, `SavedQuery`, fingerprint inputs) serializes and self-describes without a policy-local redefinition or a storage edge.

> **Why this crate exists / the core design tension.** The original `beads_rust` already shipped these exact concerns as *pure* modules: `src/policy.rs` (adaptive policy doc + evaluator, `POLICY_SCHEMA_VERSION`), `src/coordination.rs` (`br.coordination.v1`, deterministic claim classification, "Agent Mail dropped"), `src/cache.rs` (S3-FIFO kernel "replayable against traces before any storage read path depends on it"), `src/close_policy.rs`, `src/inheritance.rs`, plus a scheduler that computed scores in the CLI. unblock-policy is the consolidation of all of these into one acyclic L1 crate, with two deliberate changes vs the original: (a) the **ready hybrid sort becomes a pure policy comparator** rather than a SQL `ORDER BY` baked into storage (spine §4.1: engine `ready()` = "hybrid sort via policy"), so the ranking is unit/proptest-able without a DB; (b) all Agent-Mail-derived inputs are removed (PRD §12.1) — coordination is purely DB-state-derived data the engine passes in.

## 0. Versioning model for this crate

Two orthogonal "versions" appear in this plan and must not be conflated:

1. **Release version** `[v1] [v1.1] [v1.2] [v1.3]` — *when a file/item is introduced or changed in the product roadmap* (roadmap §6/§7: policy is touched in v1, v1.1, and v1.3; **not** v1.2). Used in the FILE BREAKDOWN "Version" column.
2. **Contract schema version** — the stable, machine-readable `unblock.<contract>.vN` string each decision contract carries (FR-12/FR-18). E.g. `unblock.scheduler.v1` (v1.1) → `unblock.scheduler.v2` (v1.3); `unblock.coordination.v1`; `unblock.gate.v1`; `unblock.close_policy.v1`. A contract-version bump is **additive only** in v1.3 (roadmap §4 risk: "must be additive, not breaking") and is surfaced to clients via `Capabilities.contract_version` (spine §5.4).

**Roadmap-driven scope per release (this crate):**
- **v1** (M1 / plan T1.1): the *pure decision primitives the v1 walking skeleton needs* — ready/hybrid-sort ranking, dependency→ready gating predicate, validation/inheritance helpers, the cache-key contract usage. (Plan T1.1 verbatim.)
- **v1.1** (LOCKED): scheduler contract (`unblock.scheduler.v1`, FR-18), coordination diagnosis (`unblock.coordination.v1`, FR-18), workflow + close gates (`unblock.gate.v1` / `unblock.close_policy.v1`, FR-19), saved-query filter-set normalization (FR-21 — the *pure* part), inheritance selection (full).
- **v1.2:** **no policy work** (roadmap §7 row: `unblock-policy` blank for v1.2 — that release is storage/sync/config remote shared-state). Listed for completeness only.
- **v1.3** (PROPOSED): scheduler v2 (critical-path / cost-aware ranking, `unblock.scheduler.v2`); active-coordination reclaim contracts (claim TTL/heartbeat decision, deterministic re-assignment evidence — still pure, still DB-derived); cache policy kernel promoted from "fields only / reserved" to an exercised S3-FIFO admission/eviction policy for the 1M-issue read path.

## 1. Public API summary (what other crates import), per release

> All types derive at least `Debug, Clone, Serialize, Deserialize, PartialEq, Eq, JsonSchema` unless noted (so the engine can pass them and MCP can self-describe them — FR-12). Time = `chrono::{DateTime, Utc}`. Errors = a per-crate `PolicyError` (snafu) exposing `fn code(&self) -> unblock_error::ErrorCode` (spine §2.1) — policy variants map to `ValidationFailed` / `PolicyViolation` / `InvalidPriority` / `InternalError`.

### v1 (M1) — consumed by `unblock-engine::Session::ready/blocked` and validation
- `pub fn ready_sort_key(issue: &Issue) -> ReadySortKey` and `pub fn cmp_ready(a: &Issue, b: &Issue) -> Ordering` — the canonical **hybrid ready sort** (priority ASC, then created_at DESC, then id ASC — fidelity to original `sqlite.rs:3464`). `ReadySortKey: Ord`.
- `pub fn is_ready(ctx: &ReadyContext) -> ReadyVerdict` — pure predicate: is an issue ready given its status, `defer_until` vs `now`, and its **incoming blocking edges' resolution state**. Encapsulates the "only `Blocks|ParentChild|ConditionalBlocks|WaitsFor` gate ready-work" rule (`DependencyType::affects_ready_work`, spine §1.4) so engine + storage share one definition.
- `pub fn is_blocked(ctx: &ReadyContext) -> bool` (the complement, for `blocked()`).
- `pub const READY_GATING_TYPES: &[DependencyType]` — the four gating edge types, re-exported for the engine's query construction.
- `pub fn cache_key_ready(filters_fingerprint: &str) -> unblock_model::CacheKey` and `cache_key_blocked(..)` — deterministic projection cache-key construction (spine §1.9 `CacheKey`; engine/storage own the actual cache store, policy only mints keys).
- `pub fn filters_fingerprint(filters: &unblock_model::ListFilters) -> String` — canonical, order-independent fingerprint of a `ListFilters` (spine §1.10, CF-C: `ListFilters` now lives in model, so policy fingerprints it directly without a storage dep).
- `pub struct ReadyContext` / `pub enum ReadyVerdict { Ready, Blocked{ by: Vec<String> }, Deferred{ until: DateTime<Utc> }, NotActionable{ reason } }` / `ReadySortKey`.
- `PolicyError` (+ `code()`).
- `pub const POLICY_CONTRACT_VERSION: &str` family root (e.g. `"unblock.policy.v1"`).

### v1.1 (LOCKED) — coordination/scheduler/gates surfaced via engine + MCP
- **Scheduler:** `pub fn rank(input: &SchedulerInput) -> SchedulerOutput` returning `unblock.scheduler.v1` evidence (ranked recommendations with per-term `evidence` + `rationale`, deterministic). Types: `SchedulerInput`, `SchedulerOutput`, `SchedulerRecommendation`, `SchedulerEvidence` (priority/dependency-impact/stale-claim/fairness/domain-contention sub-evidence), `FallbackPolicy`. Const weights (`PRIORITY_WEIGHT`, `DEPENDENT_WEIGHT`, `MAX_DEPENDENT_CONTRIBUTION`) ported from original `scheduler.rs`.
- **Coordination:** `pub fn assess_claim(input: &ClaimAssessmentInput) -> ClaimAssessment`, `pub fn coordination_status(rows: &[CoordinationClaimRow], counts: &CoordinationWorkspaceCounts, now) -> CoordinationStatusOutput` (`unblock.coordination.v1`). Types: `ClaimOwnerKind`, `ClaimClassification`, `RecommendedAction`, `ClaimAssessmentInput/Policy`, `ClaimAssessment`, `CoordinationClaimRow`, `CoordinationSummary`, `CoordinationStatusOutput`, threshold consts. **No `AgentMail*` types** (dropped, PRD §12.1) — the original's reservation-evidence enum is reduced to `ReservationEvidence::{NoSnapshot, NoReservation, Active}` carrying only caller-supplied DB-derived data.
- **Gates / close-policy:** `pub fn evaluate_close(policy: &ClosePolicy, candidate: &CloseCandidate) -> GateOutcome` and `pub fn evaluate_transition(policy: &Workflow, from: &Status, to: &Status, gates: &[GateResult]) -> TransitionOutcome` (`unblock.gate.v1`). Types: `PolicyDocument`, `ClosePolicy`, `Workflow`, `GateRule`, `GateResult`, `GateStatus`, `RequireCloseReason`, `ToggleGate`, `Attribution`, `CloseCandidate`, `GateOutcome`, `TransitionOutcome`. **The TOML deserialization of `.unblock/policy.toml` is done by `unblock-config`**, which hands policy a fully-parsed `PolicyDocument`; policy only *evaluates* (keeps policy free of file I/O).
- **Inheritance:** `pub fn select_inherited_blocks(chain: &[AncestorNode], cfg: &InheritanceConfig) -> Vec<InheritedBlock>` — pure "two bookends (immediate parent + root/epic)" selection over a caller-supplied ancestor chain (engine walks storage; policy chooses). Types: `AncestorNode`, `InheritedBlock`, `InheritanceConfig`.
- **Saved queries (pure part, FR-21):** `pub fn normalize_saved_filters(raw: &SavedQuery) -> Result<NormalizedFilters, PolicyError>` — canonical/validated filter-set (storage persists, policy validates+normalizes for deterministic cache keys).

### v1.2
- **None.** (Roadmap §7.)

### v1.3 (PROPOSED) — scale + active coordination
- **Scheduler v2:** `pub fn rank_v2(input: &SchedulerInputV2) -> SchedulerOutputV2` (`unblock.scheduler.v2`): adds critical-path-aware + estimate/cost-aware ranking terms; additive over v1 (old `rank` retained). Critical-path is computed from a caller-supplied edge list (still no `petgraph` in policy — the engine supplies precomputed longest-path/depth metrics as evidence inputs, keeping policy pure).
- **Active coordination:** `pub fn reclaim_decision(input: &ReclaimInput) -> ReclaimDecision` (`unblock.coordination.v1` additive, or `.v2` if shape breaks) — claim TTL/heartbeat staleness → deterministic reassignment recommendation + evidence.
- **Cache policy:** the S3-FIFO kernel (`S3FifoConfig`, `S3FifoCache<K,V>`, `S3FifoAdmission`, `S3FifoSegment`, `S3FifoStats`) promoted to a *used* policy for the engine's hot read projections (1M-issue gate). Trace-replayable.

## 3. Crate-level test & bench plan

- **Unit tests** (`#[cfg(test)]` per module): exhaustive per the table above; every public fn has at least the documented cases.
- **proptest (NFR-16):** (1) `cmp_ready`/`ready_sort_key` is a *total order* (antisymmetry, transitivity, totality, reflexivity of equality on tie) and deterministic; (2) all contract `rank`/`assess`/`evaluate` fns are deterministic & order-insensitive on input collection order; (3) coordination classification monotone in idle time; (4) inheritance output ≤ 2 blocks, never tombstoned; (5) cache never exceeds `max_weight`, counters consistent; (6) `filters_fingerprint`/cache-key minting order-insensitive + idempotent. Shared generators in `proptest_support`.
- **insta snapshots (NFR-14/NFR-16, CI `--check`):** golden JSON for *every* versioned contract output (`unblock.scheduler.v1/v2`, `unblock.coordination.v1`, `unblock.gate.v1`, reclaim) — explainability/stability is itself the contract; plus the `error.rs` variant→`ErrorCode` table and the `contract_versions()` list per release.
- **Contract suite (`tests/`):** the v1.3 *additive* guarantee — assert no contract schema string is ever removed and old outputs stay byte-stable when a `.v2` lands (diff-snapshot).
- **criterion (NFR-1/NFR-2):** `benches/policy.rs`; ready-sort budget aligns with the storage `ready` budget (ready 1k <5ms / 10k <50ms — the policy comparator must be a negligible fraction); 1M ready-sort + cache throughput back NFR-2 (v1.3 gate).
- **fuzz:** policy is exercised indirectly via `unblock-fuzz` (model/sync/storage ingestion); a *direct* fuzz target is **not** planned (policy takes structured, already-validated domain types — the untrusted-input boundary is the MCP/sync edge, not L1). Open question Q5 if we want a `PolicyDocument`-evaluation fuzz target once gates land.
- **No async, no I/O, no time-source mocking via clock crates:** every fn that needs "now" takes `now: DateTime<Utc>` as a parameter (testability + purity) — confirmed by the original's pure modules and required by L1.

## 4. Open questions specific to this crate

- **Q1 (ready-sort ownership / spine amendment):** the spine §4.1 says engine `ready()` does "hybrid sort via policy", but storage `ready_issues` (§3.2) returns `Vec<Issue>` and the original sorted in SQL. **Decision needed:** does storage return *unsorted* ready rows and the engine sort via `cmp_ready` (pure, testable — this plan's assumption), or does storage sort (SQL `ORDER BY`) and policy only *defines the contract* the SQL must match?
