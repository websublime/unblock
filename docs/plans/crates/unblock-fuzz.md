# unblock-fuzz — File-level Plan

**Source of truth:** PRD APPROVED v1.1 (this plan conforms to PRD §8.1 and `01-design-spine.md`; on any cross-crate type/signature disagreement, the spine wins).

**One-line purpose:** Unpublished workspace member hosting `cargo-fuzz` (libFuzzer) targets and shared harness scaffolding that exercise the untrusted-input ingestion surfaces — model content-hash/sync-equality, JSONL/`bd` import & atomic export round-trips, TOML config parsing, and storage query/import invariants — asserting "never panic / never corrupt / never escape" (NFR-16, NFR-7/8, NFR-3).

**Layer:** aux (`—` in PRD §8.1; unpublished, `publish = false`). Not part of the acyclic library DAG; it is a leaf *consumer* that sits **above** everything it tests.

**Depends-on (must stay acyclic — fuzz is a sink, nothing depends on it):**
> L0-edge convention (PRD §8.1): both L0 crates (`model`, `error`) are listed as **direct** v1 edges of `unblock-fuzz` — this row follows the "always list L0 when used" convention, matching the PRD §8.1 fuzz row (`, model, error` at v1; `config` at v1.1).
- `unblock-model` (Issue/Dependency/Comment/Event, `compute_content_hash`, `sync_equals`, `IssueValidator`, open enums) — L0, **v1** (landed T0.7).
- `unblock-error` (`ErrorCode`, `StructuredError`, `sanitize_message`, `find_similar_ids`, per-crate error `code()` views) — L0, **v1** (landed T0.7).
- `unblock-storage` (`Storage` trait + libsql local impl with the gated `testkit` seam, `ListFilters`, `IssuePatch`, `DeletePlan`) — L2 (landed T0.7; the member enables `unblock-storage/testkit`).
- `unblock-sync` (JSONL export/import, path-confinement, conflict-marker scan, bd import) — L3. **Post-T0.7:** the member does **not** depend on `unblock-sync` at T0.7 (the JSONL/`bd`/sync targets land with `unblock-sync`); the T0.7 edges are model + error + storage only.
- `unblock-config` (layered TOML resolution) — added at **v1.1** when the config target lands.
- Dev/runtime deps: `libfuzzer-sys`, `arbitrary` (derive) — **nested fuzz package only**; the member crate uses `tokio` (current-thread runtime to drive async `Storage`), `tempfile`, `serde_json`, `chrono`, `snafu` (the local `FuzzError`), and `proptest` (only for the regression-replay/smoke tests under `tests/`).

> **Acyclic guarantee:** `unblock-fuzz` is referenced by **no** other crate. It depends only on already-built layers (model/error/storage at T0.7; sync/config later). Two separate mechanisms keep nightly/libFuzzer off the stable build: (1) the `unblock-fuzz` **member** crate is excluded from `[workspace] default-members`, so the default `cargo build`/`cargo test` skip it (its `src/` cores still build on stable when targeted with `-p unblock-fuzz`); and (2) the **nested cargo-fuzz package** `crates/unblock-fuzz/fuzz` is in `[workspace] exclude` **and** declares its own empty `[workspace]` table, so it is OUTSIDE the workspace entirely (and `cargo fuzz` can build the manifest directly without cargo treating it as a member of the parent) — `cargo build --workspace` never compiles `libfuzzer-sys`/`arbitrary`, and the nested package pins its own `nightly-2026-04-01` (= rustc 1.96.0-nightly, >= the workspace's stable 1.96 target since the tree is edition 2024 + uses let-chains) via a scoped `fuzz/rust-toolchain.toml`.

> **Reshaping from `beads_rust/fuzz` (grounding source):**
> - `config_yaml` target → **`config_toml`** (D10: TOML, not the unmaintained serde_yaml fork). The YAML attack surface is gone; the TOML parse + layered-precedence surface replaces it. Lands **v1.1** with `unblock-config` full layering (v1 ships only a config *subset*; a minimal `config_toml` smoke target lands in v1).
> - `merge_issue` target (three-way merge, `ConflictResolution`, `MergeReport`) → **DROPPED** (D5: heavy git-merge coordination removed; `unblock-sync` is light export/import only). Its *valuable* invariants (determinism, validator-on-output, tombstone-never-resurrected, content_hash freshness) are **folded into** `content_hash` and `jsonl_roundtrip` targets.
> - `markdown_import` target → **DEFERRED** to whenever bulk-markdown create (FR-1a "bulk markdown import") gets its own parser surface; tracked as an open question (markdown parser location is not yet in the spine). Not in v1/v1.1 unless the parser lands.
> - `content_hash`, `jsonl_import`, `sync_cycle`, `search_issues` carry forward, retargeted to the async `Storage` trait + snafu errors + `sync_equals`/`compute_content_hash` from `unblock-model`.

## Public API summary

`unblock-fuzz` exports **no library API consumed by other crates** (it is a sink). Its "public surface" is:
1. The set of fuzz **binaries** (`[[bin]]` targets under `fuzz_targets/`) runnable via `cargo +nightly fuzz run <name>`.
2. An **internal** (crate-private) shared harness module (`src/lib.rs` + `src/*.rs`) re-used by every target and by the `tests/` regression suite. These items are `pub` only so the `fuzz_targets/*.rs` binaries (separate crates under cargo-fuzz) can import them, but they are **not** a workspace-stable API.

| Version | Harness items exposed to targets |
|---|---|
| **v1 (landed T0.7)** | `ByteCursor` + `CursorExt` (`prefix()->String`, `status`/`issue_type`/`dep_type`/`event_type`; total/panic-free on exhausted input), `tokio_block_on` (fresh `current_thread` runtime per call), `FuzzWorkspace` (tempdir + `.unblock/`) + `open_local_storage`, `normalize_issue` (idempotent repair → always `IssueValidator`-valid; clamps to the model bounds), `arbitrary_issue`/`arbitrary_issues`, the `invariants` helpers (`assert_hash_well_formed`, `assert_issue_surface_well_formed`, `assert_nonempty_structured_error`, `assert_no_raw_control`), and the local `FuzzError`. The `StorageTestkit` **seam** (gated in `unblock-storage`: `testkit_insert_raw_edge` + `testkit_child_high_water`) is what the storage cores reach via `unblock-storage/testkit`. **Post-T0.7 (with `unblock-sync`):** `FuzzWorkspace` gains the outside-sentinel + `assert_outside_untouched`/`assert_import_validation`/`assert_storage_invariants` for the JSONL/path-confinement targets. |
| **v1.1** | + `ConfigCorpus` helpers (TOML layer builders), `assert_config_precedence`. |

| Path | Responsibility | Key items | Version | Tests |

> **Structural rule (landed T0.7).** Each `fuzz/fuzz_targets/<t>.rs` is a 5-line `fuzz_target!(|data: &[u8]| { let _ = unblock_fuzz::run_<t>_case(data); })` wrapper over a `run_<t>_case` exported from the **member crate** `src/` (`src/model_targets.rs` / `src/storage_targets.rs`). This is the single most important structural rule of this crate: **all logic lives in the member `src/`, the nested `fuzz_targets/*.rs` are 5-line wrappers**, so corpus replay is testable on stable Rust. (A core returns `Err(FuzzError)` for an *operational* failure (it did not reach the deep path); an **invariant** breach `assert!`s — libFuzzer reports the panic as the crash.)

## Crate-level test & bench plan

- **Fuzz runs (manual / scheduled, nightly toolchain):** each `[[bin]]` is runnable via `cargo +nightly fuzz run <name> -- -max_total_time=…`. CI runs a **short timed smoke** (e.g. 60s/target) on a scheduled (nightly) job only — never on the stable PR gate (keeps NFR-12 stable-Rust default path clean).
- **Regression replay (stable, every PR):** `fuzz/tests/regression.rs` replays committed `corpus/` + `artifacts/` through the extracted `run_case` functions under plain `cargo test`. This is the hard gate; new crashes get their artifact committed here.
- **proptest smoke (stable):** thin `proptest!` wrappers over each `run_case` give randomized coverage on the stable PR gate without libFuzzer.
- **No criterion benches** in this crate — performance benchmarking belongs to the crates under test (`unblock-storage`/`unblock-engine` own NFR-1 criterion budgets; the NFR-3 contention lab lives in `unblock-storage`'s M0 gate). `unblock-fuzz` is correctness/robustness only. (v1.4 may add a `large_corpus` generator reused by the storage scale harness, but the bench itself stays in storage.)
- **Coverage:** `cargo fuzz coverage <target>` documented in README for periodic corpus-quality review; not gated.
- **Workspace integration:** the `unblock-fuzz` **member** crate is a `[workspace]` member but **excluded from `default-members`** (so the root `cargo build`/`cargo test` skip it; its `src/` cores + `tests/` still build/run on stable when targeted with `-p unblock-fuzz`). The **nested cargo-fuzz package** `crates/unblock-fuzz/fuzz` is in `[workspace] exclude` **and** declares its own empty `[workspace]` table — OUTSIDE the workspace, and buildable directly by `cargo fuzz` — so `cargo build --workspace` never compiles `libfuzzer-sys`/`arbitrary`, and its `fuzz/rust-toolchain.toml` pins `nightly-2026-04-01` (= rustc 1.96.0-nightly) scoped to that directory only. `forbid(unsafe_code)` + clippy pedantic apply to the member crate on stable (NFR-9/NFR-12).

## Open questions specific to this crate

1. **Async-in-libFuzzer model — RESOLVED (T0.7).** `tokio_block_on` builds a **fresh `current_thread` runtime per call** and blocks on the future: corpus determinism (a replay reproduces the same scheduling) over throughput. `claim_race` (v1.1) may use a `multi_thread` runtime when it lands.
2. **`config_toml` v1 vs v1.1 scope.** v1 ships only a config *subset* (no DB/user layers). Should the v1 `config_toml` target be a parse-only smoke, deferring all precedence assertions to v1.1 (current plan), or should even the subset precedence (CLI > env > project > defaults) be fuzzed in v1?
3. **`markdown_import` fate.** FR-1a mentions "bulk markdown import" but the spine defines no markdown parser surface. Where does that parser live (engine? a model helper?), and does it warrant a fuzz target at all, or is JSONL the only untrusted bulk-ingest path in v1? (Currently deferred/undecided.)
4. **`bd_import` corpus sourcing.** FR-26 idempotency fuzz wants a real `bd-export` sample. Can a sanitized dogfood `bd` export be committed as a seed corpus, or must it be synthesized to avoid leaking internal issue text?
5. **Dropped `merge_issue` invariants — fully covered?** Confirm that folding three-way-merge's *kept* invariants (determinism, validator-on-output, tombstone-no-resurrect, content_hash freshness) into `content_hash` + `jsonl_roundtrip` + `bd_import` leaves no untested behaviour now that 3-way merge is gone (D5). If `unblock-sync` retains *any* reconciliation (v1.2 remote), a dedicated reconciliation target may be needed earlier than v1.2.
6. **Nightly pin location — RESOLVED (T0.7); pin REPAIRED (post-T1.3).** A **scoped `crates/unblock-fuzz/fuzz/rust-toolchain.toml`** pins `channel = "nightly-2026-04-01"` (= rustc 1.96.0-nightly). Because the nested `fuzz/` package is in `[workspace] exclude` **and** declares its own empty `[workspace]` table, the toolchain file applies only inside that directory and never shadows the root stable `1.96.0` pin; the workspace build never sees nightly or libFuzzer. **Repair note:** the `fuzz-smoke` nightly leg was effectively **DOA since T0.7/T0.9** — the former `nightly-2024-10-31` pin (cargo 1.84) *predated edition 2024* (stabilized 1.85) and the workspace's let-chains (stabilized 1.88), so the `unblock-*` dep tree could not even parse under it; and the nested manifest lacked the empty `[workspace]` table, so `cargo fuzz` failed building it directly ("believes it's in a workspace when it's not"). The repair re-pins to `nightly-2026-04-01` (>= the stable 1.96 target) and adds the `[workspace]` table; the nightly cron was unwatched, so this surfaced only now.
