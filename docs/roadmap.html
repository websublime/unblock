v1.0.1Patch · planned
Maintenance patch

Orthogonal to the resequence — the dogfood-found defect set (widened by D42, the MCP argument-boundary class) + the one never-run GA validation.

  • Fix: MCP argument boundary (D42) — errors escaped the structured channel; unknown fields were silently dropped; the per-request quota missed anything under an unknown key
  • Fix: DUPLICATE JSON keys (D43) — a duplicated key collapsed last-wins while the frame was decoded, so a request whose text read as one action executed a different one; now rejected in-band, on the MCP tools/call path and on bd import lines
  • Fix: create_bulk silent markdown drops + dep.metadata discarded at L2
  • Fix: issue create with deps (D44) — the issue committed first and each declared edge landed in its own follow-up transaction, anchored on an id the client had to guess: a wrong guess left an edge-less orphan, an existing-but-wrong guess silently rewrote a THIRD issue’s dependency graph. Now one transaction, the edge source implicit (the field is omitted, a supplied one is rejected), with the cycle and duplicate guards restored — bulk create and import untouched by D44 itself (D45 later gives the shared per-record body they share exactly one guard, and re-ranks the precedence chain accordingly)
  • Fix: dangling BLOCKER id on every edge-writing path (D45) — a depends_on_id naming an issue that does not exist is accepted with isError:false and plants a permanently unresolvable blocker; now a batch-aware, in-transaction existence check with an external: carve-out, on ALL FIVE paths that write an edge (create, dep add, the JSONL/bd import leg, the issue update {parent} reparent and create_bulk) — ONE guard in the shared per-record insert body reaching three of them, with sibling guards at add_dependency and the reparent — a three-site design, not one edit. That placement REVERSES a D44 clause, which is why this repair mints its own decision id. create_bulk already refuses an unknown reference today, so what it gains is the closing of a race, not a new refusal. The EXPORT CORPUS widens with it (a row the corpus filter dropped now travels with the export whenever it stands in a dependency relation with a kept row in EITHER direction — a kept row depends on it, or it depends on a kept row, the incoming case being forced because a parent-child edge is stored on the CHILD's row and is what makes an epic parent blocked — transitively; the exporter drops nothing, because dropping the edge would turn blocked work into ready work), the external: prefix is defined once and case-INSENSITIVELY in unblock-model, and the listing view is a NEW dangling action on the diagnostics tool plus the same findings folded into the doctor report — no ninth tool, unblock-health untouched. Cut TOGETHER with D44, as its co-requisite: D44 removes the foreign-key failure that used to mask a bogus blocker id, so a release carrying D44 without this one would ship a wider hole than GA did
  • Fix: no forward-migration for the comments schema (D46) — the two D37 comments columns shipped as an in-place edit of the baseline DDL, so a database written before 2026-07-17 is stamped user_version 1 exactly like a GA one while still carrying a five-column comments table: every hydrated read fails, and unblock migrate plus unblock doctor both report success while it does. Bumping the version and running a plain ALTER does not work — both shapes carry the same stamp, so it hard-errors with duplicate column name on every database created since. The ladder is kept and bumped to 2, step 2 is an explicitly ONE-TIME shape-sensing reconcile (the only step that will ever inspect before it acts, so that from step 3 on a stamped version implies a known shape), the embedded DDL is FROZEN at the baseline shape — every post-baseline column, these two included, lives only as a step, so a fresh install now reaches the current shape by running the ladder like everyone else and every step is exercised on every install — the false green ends, and a content pin turns the next in-place DDL edit into a red build. unblock migrate is widened to observe the stamp BEFORE the repair runs (the open path migrates first, so a post-repair read could only ever print a green no-op), and it therefore prints the real delta — 1 → 2 on a stale database, 0 → 2 on a never-migrated one — a change to the numbers a shipped command prints, with no command, flag or exit code moved. No ErrorCode and no exit-table change; the stale-schema failure does gain a self-correction hint, which moves one PUBLISHED per-code byte and therefore bumps the contract unblock.mcp.v1.8 → unblock.mcp.v1.9 (additive, patch-eligible under D35)
